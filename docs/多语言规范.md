# UeePayFrontend 国际化与本地化规范

本文档是 UeePayFrontend 国际化（Internationalization，i18n）与本地化（Localization，l10n）的详细权威来源。规范以项目当前 Vue I18n 实现为基础，对齐 BCP 47、Unicode CLDR、ECMA-402 和 W3C Web 国际化原则。

项目面向金融用户端。语言切换、格式化和翻译质量不能改变资金、认证、风控、地区限制、协议或错误状态的业务含义。

## 2. 当前实现事实

本节只提供实时入口和行为边界，不固定记录启用语言数量、完整清单、接口路径或目录展开形态。执行任务时必须重新读取代码；文档不得覆盖当前实现。

### 2.1 实时入口

| 事实 | 权威入口 |
| --- | --- |
| 默认、回退、启用 Locale、规范化、持久化及 `<html lang/dir>` | `src/locales/set.js` |
| 语言包加载、英文业务回退、站点变量、View UI Plus 合并及 i18n 实例 | `src/locales/index.js` |
| 各 Locale 的真实 key、展开和嵌套结构 | `src/locales/lang/<locale>/index.js`，以 `en-US` 和目标 Locale 同时核对 |
| Vue 与 View UI Plus 安装 | `src/main.js` |
| 脚本侧统一翻译函数 `t` | `src/utils/index.js` |
| 国家、语言、时区的规范化、缓存和同步 | `src/utils/preferences.js`、`src/utils/preferences-storage.js`、`src/store/user.js` |
| 服务端开放语言与前端选项交集 | `src/views/preferences/country.vue`、`src/api/user.js` |
| 路由标题翻译与 Locale 变化响应 | `src/router/index.js` |

必须保持：

- 全项目复用 `src/locales/index.js` 导出的唯一 i18n 实例；普通翻译任务不得调整全局插件安装顺序。
- View UI Plus 使用同一实例；修改 UI Locale 合并时验证直接涉及的分页、日期、上传、表单、弹窗或空状态。
- `{siteName}` 等固定站点变量由语言入口统一注入，不在各语言包重复硬编码，也不与运行时业务插值混用。
- `warnHtmlMessage: false` 不代表允许任意 HTML 消息；富文本仍遵守本文安全规则。
- 当前初始化使用已保存语言或项目默认语言，不自动采用浏览器语言；如需改变，必须作为独立行为变更验证。
- 语言包加载和回退策略属于构建基础设施；动态加载等性能改造应独立立项。

### 2.2 语言可用性与用户偏好

语言具备三个不同状态：

| 状态 | 判断来源 |
| --- | --- |
| 前端编译支持 | `setData`、业务语言入口和 View UI Plus Locale 映射均存在 |
| 服务端当前开放 | 服务端语言列表包含该 canonical code |
| 可对用户发布 | 翻译、业务语义和必要验证通过 |

偏好页必须将服务端开放列表与 `setData` 精确取交集；任一方缺失的 Locale 都不得开放选择。`normalizeLocale()` 的语言级近似只用于映射可运行的界面语言，不代表独立支持该地区变体，也不得影响法律文本、货币、时区或地区资格判断。

国家、语言和时区是三个独立偏好。国家可以提供建议值，但不得据此推断用户真实所在地、账户国家、KYC/KYB 地区或法律资格。业务页面必须通过现有 preference 和 storage helper 读写，不直接操作缓存 key 或待同步标记；修改同步优先级、失败恢复或登出保留策略时，验证游客、登录、退出重进和跨设备场景。

### 2.3 消息结构与响应式翻译

- 新增或修改 key 前，先核对 `en-US` 与目标 Locale 的真实导出结构，不根据文件名猜访问路径。
- 所有启用 Locale 必须保持一致的 import、展开和嵌套结构；新增业务域优先使用明确命名空间。
- 调整导出结构属于破坏性变更，必须迁移 `$t`、`t`、路由 meta 和动态配置等全部调用方。
- 模板使用 `$t`；脚本优先从 `@/utils` 使用 `t`，组件局部响应式场景可使用 `useI18n()`。
- `t()` 应在 computed、render、事件或会重新执行的工厂函数中求值，不保存为不会随 Locale 重建的静态常量。
- 路由用户可见标题优先使用 `meta.titleKey`，`meta.title` 仅作兼容回退；修改后检查菜单、Header、用户中心导航和页面标题等直接调用方。

### 2.4 当前能力边界

当前不能默认声称项目已具备统一的 `numberFormats` / `datetimeFormats`、全项目 Locale-aware 格式化层、CLDR 复数自动测试、key 与插值一致性门禁、伪本地化、自动 RTL 视觉回归或翻译管理平台流程。

存量代码还可能存在硬编码文案、静态 `t()` 结果、服务端原始 `msg`、固定格式化、HTML 消息和 eager 加载成本。本次直接触及的内容必须遵守本文；安全、法律、资金结果或误导性问题优先报告，其他无关问题登记技术债并单独立项。

## 3. Locale 标识规范

### 3.1 BCP 47

Locale 标识必须使用 BCP 47 语言标签：

```text
language[-Script][-REGION]
```

示例：

```text
en-US
pt-PT
zh-CN
ar-SA
```

要求：

- 配置、目录、View UI Plus 映射和运行时状态使用同一个 canonical code。
- 使用连字符，不使用 `en_US` 一类下划线形式作为内部标准值。
- 外部输入可以被规范化，但写入偏好和运行时状态前必须映射到 `setData` 中已启用的值。
- 新增 Locale 时应使用 `Intl.getCanonicalLocales()` 或等价机制验证标签；不得自造语言代码。
- 语言选择器使用该语言的自称，如 `English`、`日本語`、`العربية`。

### 3.2 语言、书写系统、地区与业务配置

- Locale 不等于国家，不得用语言推断用户国籍、服务地区或法律资格。
- Locale 不等于币种，不得因为 `en-US` 自动把业务币种改成 USD。
- Locale 不等于时区，不得因为 `zh-CN` 自动把时间解释为 Asia/Shanghai。
- Locale 不等于 KYC/KYB、风控或产品可用范围。
- 地区、币种、时区和语言必须作为独立业务值处理。

当前项目使用 `zh-CN` 与 `zh-TW` 区分简体和繁体体验。未来如迁移到 `zh-Hans` / `zh-Hant`，必须提供兼容映射、偏好迁移和回归验证，不能直接重命名。

## 4. 语言选择、持久化与回退

### 4.1 选择顺序

当前初始化顺序：

```text
有效的已保存语言
→ DEFAULT_LOCALE
```

登录用户从服务端加载偏好后，可以通过统一偏好流程覆盖当前语言。业务页面不得再维护第二套 Locale 状态。

如果未来加入浏览器语言协商，顺序、支持列表和隐私影响必须先写入实现与测试；不得只修改文档。

### 4.2 规范化

- 所有外部 Locale 值先经过 `normalizeLocale()`。
- 精确匹配优先，再按项目现有语言映射处理。
- 未支持的值返回失败并使用默认语言，不把任意字符串写入 `<html lang>`。
- `zh-Hant`、`zh-TW`、`zh-HK` 等中文变体按当前实现映射；变更映射必须单独验证。

### 4.3 Fallback

`en-US` 是最终 fallback，但 fallback 只用于安全恢复，不是翻译完成标准：

- 已启用 Locale 的发布内容必须具备完整 key。
- 不允许依赖 fallback 长期形成一个页面混合多种语言。
- 法律协议、隐私政策、资金确认和认证说明缺失目标语言时，不得静默展示可能误导用户的混合文本。
- 缺失 key、fallback warning 或直接显示 key 必须在开发验证中记录。
- 不得把 fallback 改成中文来掩盖其他语言缺失。

## 5. Key 架构与生命周期

### 5.1 命名

Key 按业务语义分组，使用小驼峰：

```js
finance.withdrawal.submitApplication
card.status.frozen
security.twoFactor.retry
```

要求：

- 描述业务含义，不描述页面位置或颜色。
- 不使用中文原文、英文句子、随机数字或 `text1` 一类名称。
- 通用文案只在确实跨业务同义时放入 `common`。
- 相似但业务后果不同的状态不得为了复用而合并。
- 嵌套通常控制在 2 到 4 层。

### 5.2 新增、修改、移动和删除

- 新增 key 前先搜索是否已有同义 key。
- 新增或修改用户可见 key、源文案或业务含义时，必须同步 `en-US` 和所有已启用 Locale；不能完成目标语言质量复核时必须报告未验证范围，不得依赖 fallback 冒充完成。
- 移动 key 时同步所有语言包和所有调用方。
- 删除 key 前检查 `$t`、`t`、路由 meta、表格配置、动态 key 和服务端配置映射。
- 动态拼接 key 必须有有限、可搜索的枚举来源和完整 fallback，禁止由任意接口值直接组成 key。

### 5.3 翻译变更记录与语义复核

新增或修改用户可见翻译时，不能只记录“补充多语言”，必须明确本次变更的业务含义和语义差异。普通文案至少记录：

```text
Translation change:
- Key:
- Page / interaction:
- zh-CN source meaning:
- Previous meaning:
- New meaning:
- Variables:
- Locales changed:
- Risk level:
- Target-language reviewer:
- Review status: draft / reviewed / approved
```

要求：

- `zh-CN source meaning` 描述业务对象、动作、方向和结果，不只复制中文原句。
- 修改已有译文时说明旧译文哪里不准确，避免把已经审核的翻译无理由整体重写。
- 同一批量任务按业务域拆分复核；不能仅凭 key 数量一致，把所有 Locale 标记为已完成。
- 机器翻译、AI 翻译和未经过目标语言复核的内容统一标记为 `draft`。
- `reviewed` 表示已完成语义和目标语言检查；法律、资金、认证与风险文案还需业务责任人确认后才能标记为 `approved`。

语义复核至少逐项确认：

| 维度 | 检查内容 |
| --- | --- |
| 主体 | 用户、平台、银行、合作机构或服务端责任是否保持一致 |
| 动作与方向 | Recharge、转入、转出、提交、撤销、退款等资金方向是否正确 |
| 状态 | 已提交、处理中、已成功、已失败、待审核是否被准确区分 |
| 数值 | 金额、费率、上下限、数量、精度和币种是否完整保留 |
| 条件 | 否定词、资格、地区、认证等级、例外和前置条件是否缺失 |
| 时效 | 工作日、自然日、预计时间、承诺时间和时区是否被改变 |
| 责任 | 最终结果以谁为准、谁负责处理、是否构成保证或免责 |
| 交互 | 按钮是否仍执行同一动作，提示是否与当前页面阶段一致 |

## 6. 消息设计与插值

### 6.1 完整消息

每个翻译单元应是一条完整、可调整语序的消息。禁止拼接句子片段：

```js
// 不允许
t('finance.balancePrefix') + amount + t('finance.balanceSuffix')
```

推荐：

```js
t('finance.availableBalance', {
  amount: formattedAmount,
  currency: currencyCode,
})
```

目标语言可以调整变量顺序，不得被中文语序锁定。

### 6.2 插值变量

- 使用语义化命名：`{amount}`、`{currency}`、`{count}`、`{date}`、`{cardLast4}`。
- 同一个 key 在所有 Locale 中必须具有相同的运行时业务变量集合。
- 不得删除、重命名或额外添加某个 Locale 独有的必填业务变量。
- 传入翻译层前先完成金额、日期、数字和脱敏格式化。
- 用户输入和接口数据不得直接作为 HTML 插入语言包。
- 固定品牌变量可以按 Locale 选择 `{nameZh}`、`{nameEn}` 等展示形式，但必须由统一配置声明、由调用方提供完整变量并与运行时业务变量分开校验。

### 6.3 富文本

- 普通消息禁止保存大段 HTML。
- 需要链接、强调或组件时，优先使用结构化组件插值，例如 Vue I18n 的 `<i18n-t>`。
- 不得把用户输入拼进 `v-html`。
- 协议类 HTML 同时遵守安全规范中的净化和来源要求。
- 翻译不得改变链接目标、权限条件、确认行为或埋点语义。

## 7. 复数、数量和语法变化

不同语言的复数类别不只是“单数/复数”。Unicode CLDR 定义的类别包括 `zero`、`one`、`two`、`few`、`many` 和必须存在的 `other`，具体适用值由 Locale 决定。

要求：

- 数量相关消息使用 Vue I18n 的 pluralization 能力，不使用 `count === 1` 的页面级英文规则。
- 每种语言按其 CLDR 规则提供需要的形式，不能复制英文二分逻辑。
- 数字必须作为变量保留在完整消息中。
- 复数形式改变时，不能只改名词而忽略动词、代词或语序。
- `0` 不一定属于 `zero`，`1` 不一定在所有语言中只对应 `one`；以 Locale 规则为准。
- 小数可能使用与整数不同的复数类别。

最低测试值：

```text
0, 1, 2, 3, 5, 11, 21, 100, 1.5
```

阿拉伯语等具有多种复数形式的 Locale 必须单独人工复核。新增复数消息前应先查 Vue I18n 当前版本的消息语法和对应 CLDR 规则，不凭印象排列分支。

## 8. 数字、金额、百分比和单位

### 8.1 计算与展示分离

- 金额计算继续使用 `decimal.js` 或项目统一金额工具。
- `Intl.NumberFormat`、Vue I18n `$n` 或等价封装只负责展示，不参与资金计算。
- 业务值保持原始数值和 ISO 货币代码，不能把格式化字符串回传接口。

### 8.2 Locale-aware 格式化

目标实现应基于 ECMA-402：

- 数字：`Intl.NumberFormat`。
- 货币：`Intl.NumberFormat` + 明确的 ISO 4217 currency。
- 百分比：`style: 'percent'`，确认接口值是 `0.1` 还是 `10` 后再格式化。
- 列表：`Intl.ListFormat`。
- 相对时间：`Intl.RelativeTimeFormat`。
- 排序和搜索：需要语言规则时使用 `Intl.Collator`。

要求：

- 不在语言包中硬编码千分位、小数点或货币符号。
- 不通过 Locale 猜测业务币种。
- USD、EUR、CNY 等代码是否展示由业务语义决定；金融详情中优先避免只有 `$` 的歧义展示。
- 精度由币种规则和业务规则共同决定，不用 `Number` 浮点运算先截断资金。
- 用户输入金额的解析不能简单反转格式化结果；输入规则必须明确允许的十进制格式。
- 机器交换值、API 参数、数据库字段和可重导入 CSV 不做本地化转换。

当前项目尚未建立统一 `numberFormats`。在该能力落地前，新增格式化应优先复用现有工具；如需引入统一层，应作为独立工程改造并回归所有资金页面。

### 8.3 Unicode 文本、排序与搜索

- 源文件、语言包和接口文本统一使用 UTF-8。
- 不假设 JavaScript `string.length` 等于用户看到的字符数；姓名、说明和短信长度涉及组合字符或 emoji 时，应按产品和服务端规则处理。
- 面向自然语言的大小写转换使用明确 Locale；API key、币种代码、枚举和技术标识不得按用户 Locale 改写。
- 需要面向用户排序时使用 `Intl.Collator` 或统一封装，不按 Unicode code unit 顺序冒充语言排序。
- 搜索是否忽略大小写、重音符号、全半角或变音符必须由产品语义决定，并与服务端保持一致。
- 不得对密码、Token、签名、地址、卡号或其他精确标识做 Unicode 规范化、大小写转换或本地化。
- 字体和布局必须覆盖已启用语言的字形、组合字符、无空格文本和行高，不能通过截断掩盖缺字。

## 9. 日期、时间、时区和日历

- Locale 决定展示习惯，时区决定时间对应的实际时刻，两者必须分开。
- 接口交换优先使用明确时区的 ISO 8601 时间或项目既有协议。
- 展示使用 `Intl.DateTimeFormat`、Vue I18n `$d` 或统一封装。
- 不在语言包中拼接年、月、日、时、分。
- 绝对时间在跨地区或可能产生歧义的场景应显示时区或明确说明账户时区。
- 日期范围必须明确包含边界，避免把本地日历日期错误转换成 UTC 前一天或后一天。
- 涉及夏令时的地区必须验证跨 DST 的日期和时间。
- 不使用 Locale 自动改变服务端业务日、账务日或结算时区。
- 当前项目默认公历行为；如未来支持其他日历系统，必须明确输入、存储和展示边界。

当前项目部分工具仍使用固定 `en-US` 或固定模板格式。这是存量实现事实，不代表所有用户界面已经 Locale-aware；相关迁移遵守存量技术债边界，不在无关任务中全量重写。

## 10. RTL 与双向文本

### 10.1 页面方向

- 切换 Locale 时必须同步 `<html lang>` 和 `<html dir>`。
- RTL 页面以 HTML `dir="rtl"` 作为文档方向来源，不能只靠 CSS `direction` 模拟。
- 新增 RTL Locale 时必须在 `setData` 明确配置方向，不能仅根据语言代码猜测。

### 10.2 布局

- 新样式优先使用逻辑属性：`margin-inline-start`、`padding-inline-end`、`inset-inline`、`border-start-start-radius`。
- 避免把 `left`、`right` 当作“开始”和“结束”；真实物理方向含义除外。
- 返回、前进、步骤箭头等方向性图标按语义镜像。
- Logo、支付品牌、播放、下载、勾选和无方向语义图标不得机械镜像。
- 表格列顺序、抽屉、分页、日期选择器、图表、导航和弹窗必须在 RTL 下实际检查。

### 10.3 混合方向内容

- 卡号、IBAN、邮箱、URL、API key、代码、币种代码和拉丁数字通常保持 LTR。
- 在 RTL 句子中嵌入方向未知的用户或接口文本时，优先使用 `<bdi>` 或 `dir="auto"` 隔离。
- 只有明确知道内容方向时才设置 `dir="ltr"` 或 `dir="rtl"`。
- 不在翻译字符串中随意加入不可见双向控制字符；必须使用时要有注释和针对性测试。

## 11. 翻译语义、术语与质量

### 11.1 语义源与 fallback 的区别

当前团队以 `zh-CN` 作为业务含义确认基准，以 `en-US` 作为运行时最终 fallback。两者职责不同：

- 中文负责确认业务对象、动作、条件和风险含义。
- 英文必须达到可以直接面向用户的完整质量。
- 其他 Locale 按已确认业务含义进行自然本地化，不按中文词序逐字替换。
- 中文原文有歧义时先确认业务，不允许译者或 AI 自行补充规则。

### 11.2 术语

统一使用：

```text
UeePay
Virtual Card
Physical Card
Cardholder
Recharge
Withdrawal
Transaction
KYC / KYB / Verification
Risk Control
Webhook / Callback
```

- 同一业务术语在页面、状态、帮助中心和协议中保持一致。
- 翻译记忆或术语表不能覆盖当前产品定义。
- API 枚举值、内部错误码和字段名不得直接展示给用户。
- 按钮使用明确动作，状态使用稳定结果或阶段名称。

以下相近概念不得合并翻译：

| 概念 | 当前业务含义 |
| --- | --- |
| Account Recharge | 向用户账户余额充值 |
| Card Transfer In | 从账户余额向卡内余额转入 |
| Card Transfer Out | 从卡内余额转回账户余额 |
| Card Opening / Issuance | 创建或发行卡片 |
| Card Activation | 激活已经创建的卡片 |
| Authorization | 卡交易授权，不等同于认证或登录授权 |
| Reversal | 撤销尚未完成结算的交易，不等同于 Refund |
| Refund | 对已完成或已入账交易发起退款 |

目标语言可以使用自然表达，但必须保留上述对象、资金方向和状态差异。

### 11.3 金融、认证和法律文案

- 不增加、删除、弱化或扩大金额、费用、时效、资格、地区、审核和风险条件。
- “已提交”“处理中”“已成功”“已失败”必须准确区分。
- 禁止翻译成“秒到”“保证通过”“绝对稳定”“无限制”等承诺。
- 法律协议和隐私政策需要记录适用 Locale、版本和业务复核状态。
- 未经批准的机器翻译不能作为法律文本的最终版本。
- 目标语言法律文本缺失时，必须明确展示可用版本和适用说明，不能用局部 fallback 拼成混合协议。
- “持牌”“符合某法规”“已取得某认证”、响应时限、删除时限、保存年限、赔偿范围和争议管辖等事实必须先由法务或业务责任人确认，翻译人员不得自行补充。
- 每个法律 Locale 至少记录 `version`、`effectiveDate`、`sourceLocale`、`reviewer` 和 `reviewStatus`；只有 `approved` 状态可以作为对应 Locale 的正式法律版本。
- 法律原文变化后，旧译文自动回到 `draft`，不得因为 key 和 HTML 结构仍一致而继续沿用原审核状态。
- 未完成批准时，应由产品和法务决定明确展示受支持的正式版本、提示用户当前文本语言，或暂不开放该 Locale；前端不得自行宣称翻译已获批准。

### 11.4 翻译质量

- 使用目标语言自然语法、语序、标点、大小写和产品表达。
- 机器翻译只能作为草稿，必须进行语义复核和目标语言质量复核。
- 短按钮、标题和状态必须结合交互上下文，不能脱离页面逐词翻译。
- 翻译应提供必要上下文：页面、用户动作、系统动作、变量含义、字符限制和风险等级。
- 不用相同 key 表达多个不同语境，避免英文同词但其他语言无法共用。

## 12. 文件组织与调用

### 12.1 文件组织

语言包按业务域拆分：

```text
src/locales/lang/<locale>/common.js
src/locales/lang/<locale>/finance.js
src/locales/lang/<locale>/card/detail.js
src/locales/lang/<locale>/open-platform.js
```

- `common.js` 只存放真正跨业务通用的内容。
- 同一业务域在所有 Locale 中使用相同文件和对象结构。
- 新增文件后在该 Locale 的 `index.js` 中显式导出。
- 不把所有页面文案堆入一个文件。
- 协议、隐私政策等长文本应按章节和段落保持可读源码与稳定 diff，不保存为难以逐段审核的单行超长转义字符串。
- 法律文本的版本与审核元数据不得混入普通用户文案 key；应使用明确的数据结构或独立元数据入口，并保证运行时只展示已选择的正式版本。

### 12.2 调用

模板使用 `$t`：

```vue
<Button>{{ $t('button.confirm') }}</Button>
```

脚本和配置优先使用项目统一出口：

```js
import { t } from '@/utils'
```

- 不在业务页面创建第二个 i18n 实例。
- 不绕过 `src/locales/index.js` 自行维护另一套消息。
- 需要响应 Locale 变化的派生文案必须放在 computed、渲染函数或可重新执行的流程中，不能只在模块初始化时固定一次。
- 路由标题、表格列、状态映射和校验消息同样属于用户可见内容。
- 国家名称优先使用 `countries.json` 的 `name_key`，原始 `name` 只作为兼容 fallback。
- 服务端返回的币种代码、银行名、卡组织和业务标识可以原样显示；服务端返回的状态、错误和操作文案不能因此绕过 i18n。

## 13. 硬编码与存量治理

必须进入 i18n：

- 按钮、菜单、Tab、表头、筛选和分页。
- label、placeholder、校验、帮助文本。
- Toast、Notice、Modal、Alert 和错误恢复。
- loading、empty、success、warning、failure。
- 认证、资金、卡片、Recharge、提现、开放平台和法律文案。
- 图片替代文本、`aria-label`、tooltip 和仅图标操作名称。

可以保持原值：

- API 字段名和协议枚举。
- 币种代码、卡组织、银行正式名称等业务标识。
- 不展示给用户的日志标识和内部注释。
- 明确要求保持原文并标注语言的法律原件。

存量硬编码遵守文档治理规范：

- 本次新增或直接触及的用户可见文案必须完成国际化。
- 同文件但无关的存量硬编码不自动扩大任务，可登记技术债。
- 安全、法律、资金结果或可能误导用户的硬编码不适用普通存量豁免。
- 批量清理必须作为独立任务，不能借局部翻译修改重写全站。

## 14. 新增或开放 Locale

新增 Locale 按以下顺序：

1. 确认产品范围、翻译责任人和目标语言质量来源。
2. 选择并验证 BCP 47 Locale。
3. 明确 `dir`、View UI Plus 支持、数字、货币、日期、复数和字体要求。
4. 创建完整业务语言包并保持 key、变量和文件结构一致。
5. 完成术语、金融、认证、错误和法律文案复核。
6. 确认 `/user/languages` 可以返回该 canonical code，并与 `setData` 取交集。
7. 完成游客偏好、登录用户偏好、待同步和服务端保存验证。
8. 完成桌面端、移动端、长文本、复数和 RTL 验证。
9. 最后同时开放前端 `setData` 和服务端语言列表。

禁止先开放语言选项，再依赖 `en-US` fallback 慢慢补翻译。

当前已经开放的 Locale 如发现质量缺口，应记录风险和整改范围；是否临时下线属于产品与业务决策，不能由文档任务自行处理。

## 15. 验证与质量门禁

### 15.1 结构检查

- 所有已启用 Locale 的 key 集合一致。
- 同名 key 的插值变量集合一致。
- 所有消息均可由当前 `@intlify/message-compiler` 正常编译；普通文本中的 `@`、`|`、`{`、`}` 必须按 Vue I18n 消息语法处理。
- 复数消息包含该 Locale 所需分支。
- 页面引用的静态 key 存在。
- 删除和移动的 key 没有残留引用。
- 每个 `setData` Locale 都有业务入口和 View UI Plus 映射。
- Locale code、目录名、映射键和 `<html lang>` 一致。

动态 key 无法完全通过静态扫描证明时，必须提供枚举测试。

结构检查通过只说明语言包可以加载，不代表译文语义、法律效力或目标语言质量已经通过。

### 15.2 内容检查

- 目标语言自然、专业，不是逐字机器翻译。
- 术语、变量、数字、URL 和品牌名没有误译。
- 资金状态和系统结果没有被扩大或弱化。
- 法律、KYC/KYB、风控和地区限制经过额外复核。
- 文案长度适配按钮、表格、移动端和弹窗。
- 所有真实或示例敏感信息均已脱敏。

### 15.3 运行时检查

- 切换语言无需刷新，页面没有半旧半新状态。
- `<html lang>` 与 `<html dir>` 正确更新。
- Console 没有 missing key、fallback 或消息编译错误。
- View UI Plus 日期、分页、上传、弹窗等组件语言一致。
- 路由跳转前后以及原地切换语言后，`document.title`、Header、移动端菜单、用户中心菜单和 `UiPage` 标题一致。
- 偏好页只展示 `setData` 与 `/user/languages` 的交集。
- 游客保存后待同步标记正确，登录同步成功后清理；同步失败不丢失当前浏览器偏好。
- 登录用户保存时先确认服务端成功，再应用本地偏好；失败时保留可恢复状态。
- 国家建议语言和时区不会覆盖用户随后明确选择的值。
- 登录、2FA、451、KYC/KYB、资金和卡片关键流程没有因翻译中断。
- RTL 下导航、表单、表格、抽屉、弹窗、分页和混合方向文本正确。

### 15.4 格式化检查

- 数字覆盖 0、负数、小数、大数和分组分隔。
- 复数覆盖 `0, 1, 2, 3, 5, 11, 21, 100, 1.5`。
- 货币覆盖实际支持币种、零值、负值和业务精度。
- 日期覆盖月末、年末、闰日、时区差异和夏令时边界。
- 长文本、无空格语言和 CJK 文本不会溢出或错误截断。

### 15.5 项目文件验证矩阵

| 变更类型 | 至少检查 |
| --- | --- |
| 普通翻译 key | 目标业务语言文件、所有启用 Locale 的同路径文件、页面调用方 |
| 新增业务语言文件 | 每个 Locale 的同名文件与 `index.js` 导出结构 |
| 新增或调整 Locale | `set.js`、`locales/index.js`、View UI 映射、`/user/languages`、偏好页 |
| 偏好保存或同步 | `GlobalPreferences.vue`、`preferences/country.vue`、`preferences.js`、storage helper、userStore、user API |
| 路由标题或菜单 | 路由 meta、`router/index.js`、Header、移动端菜单、用户中心导航、`UiPage` |
| 日期或时区 | `preferences.js`、日期组件、格式化工具、API 时间协议和目标页面 |
| 数字或金额 | Decimal 计算链路、展示格式化、表格、详情、导出和移动端 |
| RTL | `setData.dir`、HTML `lang/dir`、全局布局、目标组件、方向性图标和混合方向文本 |
| View UI Plus 文案 | `main.js` i18n 回调、`viewUiLocales`、对应组件运行时展示 |

## 16. 交付记录

涉及多语言的任务，完成回复或 PR Validation 必须引用第 5.3 节的翻译变更记录，不重复维护 `Source meaning`、`Locales changed` 等相同字段；在此基础上至少补充以下验证结果：

```text
I18n validation:
- Translation change record: attached / not applicable
- Key and variable parity:
- Plural and formatting:
- RTL:
- Runtime pages:
- Financial / compliance review:
- Fallback observed:
- Unverified scope:
```

只有文档修改时，按项目规则不自动运行构建；实际语言包、Locale 切换、格式化或 RTL 实现发生变化时，按风险范围执行浏览器验证。

## 17. 禁止事项

- 禁止只修改 `zh-CN`，却声称完成所有已启用语言。
- 禁止依赖 fallback 掩盖缺失翻译。
- 禁止拼接句子、硬编码语序或页面级手写英语复数规则。
- 禁止用 Locale 推断币种、时区、国籍、权限或法律资格。
- 禁止把格式化后的展示值作为资金计算或 API 输入。
- 禁止把 API 错误码、枚举、堆栈或上游原文直接展示给用户。
- 禁止在语言包中保存 PAN、CVV、OTP、证件号、Token、密钥或真实用户资料。
- 禁止直接交付未经语义和目标语言复核的机器翻译。
- 禁止通过翻译改变审核状态、资金结果、服务范围或风险提示。
- 禁止只修改 CSS `direction` 而不维护 HTML `lang` / `dir`。
- 禁止将“计划支持”写成“当前已经支持”。
