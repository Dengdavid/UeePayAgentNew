# UeePayFrontend 文档治理与冲突处理规范

本文档定义项目规则的职责边界、优先级、冲突裁决、临时例外和维护方式。目标是让不同文档可以组合执行，同时避免“更严格”“更安全”等模糊表述造成任意解释。

## 1. 适用范围

以下情况必须使用本文档：

- 上级与子项目 `AGENTS.md` 表述不同。
- `AGENTS.md` 与专项规范表述不同。
- 两份专项规范同时适用但要求无法同时满足。
- 文档描述与当前代码、配置、脚本或目录不一致。
- 用户要求与默认工作流边界不同。
- 需要为单次 Issue、分支或 PR 增加临时例外。

## 2. 规则类型

先判断规则类型，再判断优先级。

| 类型 | 示例 | 处理原则 |
| --- | --- | --- |
| 安全与合规底线 | 权限、资金、KYC/KYB、2FA、风控、脱敏 | 累积生效，不得被下级规则弱化 |
| 用户授权边界 | 只读、诊断、修改、构建、提交 PR | 采用最小必要授权，不自动扩大任务 |
| 领域实现规则 | 组件、路由、Store、多语言、构建 | 由对应专项规范负责详细规则 |
| 工作流规则 | Issue、分支、commit、PR、验证 | 由 GitHub 和测试/构建规范共同负责 |
| 描述性事实 | 当前组件名、脚本、fallback、目录 | 以实时代码和配置为当前事实 |
| 建议与示例 | 推荐提示词、示例命令、参考阈值 | 不能覆盖强制规则或真实能力 |
| 临时例外 | 某 Issue 排除某文件 | 必须限范围、可追踪、可失效 |

## 3. 文档职责

| 来源 | 职责 |
| --- | --- |
| 上级 `../AGENTS.md` | 多子项目共同安全底线和仓库级工作原则 |
| 项目 `AGENTS.md` | UeePayFrontend 强制规则、任务触发和授权边界 |
| `docs/README.md` | 文档导航、领域所有权和冲突入口 |
| `docs/技术规范.md` | 前端通用工程基线 |
| 专项规范 | 对应领域的唯一详细规则来源 |
| `README.md` | 项目介绍、当前命令和开发入口 |
| 当前代码和配置 | 当前实现事实，不自动代表推荐做法 |
| Issue / PR | 单次需求、验收标准和临时例外 |

同一规则只保留一个详细权威来源。其他文档只保留触发条件、摘要和链接。

### 3.1 按需读取边界

文档读取采用“先路由、再检索、后扩展”的顺序：

1. 先通过项目 `AGENTS.md` 和 `docs/README.md` 判断任务领域，只选择直接相关的候选文档。
2. 对候选文档先检索标题、字段名、路由名、组件名、错误信息或其他任务关键词，再读取命中章节及必要的相邻内容。
3. 命中章节引用其他章节或规范时，只跟进完成当前判断所必需的引用，不递归读取全部链接。
4. 多领域规则同时适用时，分别读取各文档的相关章节，并按第 4 节裁决；“可能相关”不构成全文读取理由。

仅在以下情况扩大读取范围：

- 局部章节缺少定义、前置条件或例外，无法独立判断。
- 规则存在冲突，必须核对各自完整约束。
- 涉及安全、资金、权限、认证、风控、敏感信息或合规底线，需要确认关联限制。
- 文档本身是本次检查、重构或一致性审查对象。

扩大范围应从被引用章节或相邻章节开始；只有规则分散在全文且无法通过标题或关键词定位时才阅读全文。不得以“熟悉项目”“确保没有遗漏”为由默认全文读取上级规则、文档索引或全部专项规范。

## 4. 冲突裁决顺序

按以下步骤处理，不直接使用“哪条看起来更严格”作为唯一依据：

1. 检查是否涉及安全、资金、权限、认证、风控、敏感信息或合规底线。
2. 确认用户本次授权是只读、诊断、修改、构建还是发布。
3. 确认目标文件所在子项目和最近的 `AGENTS.md`。
4. 根据任务领域选择专项规范。
5. 检查当前代码、配置、命令和目录事实。
6. 尝试同时满足所有兼容规则。
7. 仍无法同时满足时，按下表裁决或停止请求确认。

| 冲突 | 裁决 |
| --- | --- |
| 安全底线与便利性冲突 | 安全底线优先 |
| 用户授权与自动优化冲突 | 最小授权优先 |
| 上级通用实现与子项目具体实现冲突 | 子项目具体规则优先，但不得弱化上级安全底线 |
| 通用技术规范与专项规范冲突 | 专项规范负责该领域 |
| 两份专项规范跨领域冲突 | 取可同时满足的交集；无交集时停止确认 |
| 文档事实与代码事实冲突 | 代码决定当前事实，文档决定目标；先报告差异 |
| 示例与强制规则冲突 | 强制规则优先 |
| 历史例外与当前任务冲突 | 当前任务范围优先；无有效期例外视为失效 |

## 5. 授权边界

### 5.1 只读与诊断

“检查”“分析”“为什么”“评估”只授权读取和报告，不自动授权：

- 修改代码或文档。
- 安装依赖。
- commit、push 或创建 PR。
- 发送外部消息。

### 5.2 修改与优化

“修改”“修复”“优化”授权当前需求范围内的文件变更，但不自动授权：

- 改动无关模块。
- 新增大型依赖。
- commit、push 或创建 PR。
- 绕过安全、认证或权限边界。

### 5.3 构建与完整验收

“构建”“完整验证”“完成项目”“性能优化”授权按构建与性能规范执行检查；如果需要懒加载或资源整改，可以在当前任务范围内实施并复测。

### 5.4 提交 PR 与更新 PR

“提交PR”“创建PR”“更新PR”只授权发布当前已有目标 diff，并立即进入 no-edit。风险分级、暂存、commit、push 和 PR 操作由 `docs/GitHub工作流规范.md` 负责，触发后的构建与性能执行由 `docs/构建发布与性能规范.md` 负责；验证需要改文件时停止发布，用户确认整改后退出 no-edit，修复完成后需再次明确提交或更新 PR。

## 6. 当前事实与目标规范

文档与代码不一致时，分开处理：

```text
当前事实：实时代码、配置、脚本和目录现在是什么。
目标规范：团队希望后续代码遵守什么规则。
```

处理要求：

- 不得把旧文档描述当作已验证事实。
- 不得为了让代码匹配文档而擅自改变业务行为。
- 描述性错误应优先修正文档。
- 规范性差异如需要改代码，应作为独立实现任务并验证。
- 当前事实可能变化的文档，应引用真实入口文件，避免复制大段易漂移列表。

## 7. 存量代码与技术债边界

规范生效不代表自动授权全仓库整改。发现存量实现与当前规范不一致时，按以下边界处理：

| 场景 | 处理方式 |
| --- | --- |
| 本次新增代码 | 必须符合当前规范 |
| 本次直接修改的代码或业务流程 | 在不破坏兼容性的前提下同步符合当前规范 |
| 同文件但与本次需求无关的存量问题 | 不顺手修改，记录为技术债 |
| 因共享组件、请求层、路由或 Store 改动而受到直接影响的调用方 | 属于必要影响范围，必须检查并验证 |
| 安全、资金、权限、认证、风控或敏感信息问题 | 不适用存量豁免；先停止风险操作并报告 |
| 需要批量迁移或架构调整 | 拆分为独立任务，明确范围、验证和回滚方式 |

“触及范围”按实际行为和依赖链判断，不按“整个文件都算本次范围”扩大解释。仅为满足文档而修改无关存量代码，属于越权重构。

存量问题需要跟踪时使用：

```text
Technical Debt:
- Rule:
- Current implementation:
- Files or flow:
- Risk:
- Why not fixed in current task:
- Suggested scope:
- Verification:
- Issue:
```

没有对应 Issue 时可以在交付结果中记录，但不得假装已经完成整改。

## 8. 临时例外

临时例外必须记录：

```text
Exception:
- Issue / PR:
- Branch:
- Rule being overridden:
- Files or scope:
- Reason:
- Approved by:
- Start:
- Expiry or removal condition:
- Security impact:
- Follow-up:
```

禁止：

- 在根 `AGENTS.md` 永久排除某个业务文件。
- 使用“这次不用提交”形成所有后续任务的默认规则。
- 省略 Issue、范围或失效条件。
- 通过临时例外绕过权限、认证、资金或敏感信息规则。

## 9. 冲突记录

遇到无法直接裁决的冲突时，使用：

```text
Conflict:
- Rule A:
- Rule B:
- Type:
- Target scope:
- Current implementation:
- Decision:
- Rationale:
- User confirmation required:
- Documents to update:
```

冲突解决后，应更新所有直接冲突的权威文档，不能只在聊天中说明。

## 10. 当前统一决定

- UeePayFrontend 日期和日期区间共享组件使用 `FormDateBox`，月份使用 `FormMonths`。
- Commit 新功能类型遵守上级仓库固定值 `feature`；子项目不得同时推荐 `feat`。
- Issue-first 约束适用于 Issue 分支、commit 和 PR；用户只授权本地修改时可以先形成未提交 diff，但不得自动创建 Issue、切分支或发布。
- PR 发布按最终 diff 的风险等级验证；纯文档、非用户可见注释和局部无逻辑样式属于低风险，不强制构建或浏览器验收，其他等级按 GitHub、测试和构建规范执行。
- `src/api/request.js` 不存在永久排除规则，是否提交取决于当前 Issue、用户要求和目标 diff。
- 多语言默认与兜底语言以 `src/locales/set.js` 的 `DEFAULT_LOCALE`、`FALLBACK_LOCALE` 为当前事实。
- 存量实现不因新规范自动进入当前任务；新增代码、本次触及流程和安全问题按第 7 节处理。

这些决定对应实现变化时，必须同步更新本节和相关专项规范。

## 11. 文档维护

- 新增或修改强制规则时，先确认详细权威来源。
- 同一变更涉及多个文档时，同一次任务完成同步更新。
- 删除重复规则时保留链接，不让使用者失去入口。
- 文档中的命令必须真实存在；未来计划必须明确标记为尚未实现。
- 组件、路由、Store、语言、脚本等描述应定期与代码核对。
- 文档变更完成后运行 `yarn docs:check`，并检查目标 diff 与无法自动判断的语义冲突。
