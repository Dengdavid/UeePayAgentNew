# UeePayFrontend 组件使用规范

本文档是 `UeePayFrontend` 组件选择、组件清单、封装、修改、兼容和删除规则的详细权威来源。项目是金融行业用户端，组件改动可能影响注册登录、KYC/KYB、虚拟卡、实体卡、Recharge、提现、财务流水、Express、开放平台和安全设置。任何组件级修改都必须优先保证兼容性、权限边界、敏感信息脱敏、资金展示准确和移动端可用性。

## 1. 组件分层

当前项目组件主要分为：

```text
src/components/form        表单、筛选、上传、日期、表格等老组件体系
src/components/uiForm      用户中心常用页面、表格、tabs、状态、空态等 UI 组件
src/components/layout      全局布局、Header、Footer、CardBox、加载和错误容器
src/components/com         通用展示组件，如 IconBox、CardTotalBox、TipBox
src/components/ui          较新的基础 UI 组件，如 cell、table、tabs、encrypt-text
src/components/cardholder  持卡人动态表单和合规资料组件
src/views/ucenter/components 用户中心业务组件，如 2FA、安全、开放平台
src/components/wap         移动端布局组件
```

AI 必须先判断目标需求属于“页面组合”“通用 UI”“表单输入”“业务组件”还是“布局组件”，再决定复用或新增组件。

## 2. 组件选择优先级

优先级从高到低：

1. 目标页面已有且符合当前 `AGENTS.md` 与专项规范的局部组件和既有写法。
2. `src/components/uiForm` 中的用户中心组件。
3. `src/components/form` 中已全局注册的表单和表格组件。
4. `src/components/layout`、`src/components/com`、`src/components/ui` 中的通用组件。
5. View UI Plus 原生组件。
6. 新增局部组件。
7. 新增全局共享组件。

要求：

- 已有组件能满足需求时，不新建同类组件。
- 页面既有写法与表单、路由、Store、安全等专项强制规则不一致时，以对应专项规则为准，不得以“保持旧写法”为由继续新增旁路实现。
- 新增组件前必须搜索是否已有功能相近组件。
- 新增共享组件必须有至少两个明确调用场景，或能明显降低高风险重复逻辑。
- 页面一次性需求优先写局部组件，不要进入全局注册。
- 不擅自引入新的 UI 库、图标库、动画库或 CSS 框架。

## 3. 全局注册与导出边界

`src/utils/components.js` 是当前全局注册组件的主要来源。`src/utils/plugin.js` 也导出部分工具和 UI 组件。

修改要求：

- 新增全局组件时，必须同步检查命名、导入、导出和实际使用场景。
- 删除组件时，不能只删 `.vue` 文件，必须同步清理注册文件和所有引用。
- 审计组件使用时，不能把 `src/utils/components.js` 的注册当作真实业务使用。
- 搜索模板调用时要同时检查 PascalCase 和 kebab-case。
- 修改全局组件前必须搜索调用方，评估财务、卡片、认证、Express、开放平台等页面影响。

## 4. 页面容器组件

推荐使用：

- `UiPage`：列表页、搜索、分页、loading、empty、移动端搜索等页面容器。
- `CardBox`：标准白卡容器。
- `UiTabs`：用户中心 tabs 和移动端兼容 tabs。
- `UiCell`、`UiTips`：信息分区和提示内容。

使用规则：

- 用户中心列表页优先使用 `UiPage` 或现有页面容器，不要手写一套分页、搜索、空状态。
- 普通内容区优先使用 `CardBox` 保持白卡风格。
- tabs 逻辑优先使用 `UiTabs`，不要用多个按钮临时模拟导航。
- 页面级操作优先使用页面容器提供的标准操作区：`UiPage` 无筛选栏时在标题区域展示操作，有筛选栏时将操作与筛选栏统一排列，移动端使用底部操作区；页面不得另建位置冲突的操作栏。
- 新增页面容器样式应 scoped，避免污染其他页面。
- 修改 `UiPage`、`UiTabs`、`CardBox` 必须搜索所有调用方并说明风险。

## 5. 表单组件规范

常用组件：

```text
FormItemBox
FormInput
FormSelectBox
FormDateBox
FormMonths
FormCheckbox
FormRadio
FormSwitch
FormUpload
FormUploadImg
FormUploadInput
FormImg
FormCode
FormPup
FormPupBox
```

要求：

- 表单字段必须有可见 label，不用 placeholder 代替 label。
- 输入框、下拉框、日期、开关、单选、复选、文本框上传、弹窗和表单项校验分别优先使用 `FormInput`、`FormSelectBox`、`FormDateBox`、`FormSwitch`、`FormRadio`、`FormCheckbox`、`FormUploadInput`、`FormPupBox` 和 `FormItemBox`；只有对应组件无法满足明确业务需求时才使用 View UI Plus 原生组件。
- 金融、KYC/KYB、提现、卡片、开放平台表单必须保留必填、校验和服务端字段。
- 异步提交必须有 loading 或 disabled，避免重复提交。
- 错误提示应靠近字段，并说明如何修正。
- 日期、月份、区间选择优先使用现有 `FormDateBox`、`FormMonths`。
- 上传 KYC/KYB、证件、合规资料时必须限制展示范围，不把原始文件地址或敏感信息暴露在页面或日志中。
- 修改 `FormDateBox`、`FormSelectBox`、`FormInput` 等共享 wrapper 前必须搜索调用方。

## 6. 表格组件规范

常用组件：

```text
FormTable
UiTable
UiTableWap
UiTableSelect
SuperTable
TableBox
```

使用规则：

- 旧页面或已有 `FormTable` 的页面继续沿用 `FormTable`，避免混用导致交互割裂。
- 用户中心新列表优先评估 `UiPage` + `UiTable` / `UiTableWap`。
- 移动端数据列表要考虑 `UiTableWap` 或卡片化，不让普通表格强行溢出。
- 金额列、日期列、状态列、操作列应保持格式统一。
- 状态不能只用颜色表示，必须有文本或状态组件。
- 操作列中的详情、确认、删除、冻结、解冻等动作必须保留权限和二次确认逻辑。
- 表格 loading、empty、分页、刷新不能因 UI 优化被删除。

## 7. 状态、金额与敏感字段组件

推荐：

- 状态：`FormDot`、`UiDot`、`FormOptionsText`、`dot-text`。
- 统计：`UiCounts`、`CardTotalBox`。
- 敏感文本：优先使用已有脱敏组件或业务组件，如 `encrypt-text`、卡号展示相关组件。
- 图片：`UiImg`、`ImgBox`、`FormImg`；图片及图片组件必须遵守 `docs/构建发布与性能规范.md` 第 9.1 节的默认懒加载要求。

强制要求：

- 卡号 PAN、CVV、OTP、证件号、密钥、KYC 文件地址不得完整展示。
- 金额展示不得使用浮点数计算结果直接渲染，优先使用后端值或 `decimal.js` / 项目金额工具。
- 金额、手续费、汇率、奖励、余额等字段应使用稳定数字对齐和统一币种标识。
- 敏感字段 reveal 必须依赖服务端权限，前端只控制交互展示。
- 复制按钮不得复制完整敏感信息，除非业务明确且经过权限/2FA/风控结果允许。

## 8. 业务组件规范

`src/views/ucenter/components` 内组件多与账户安全、2FA、开放平台、登录设备相关。

要求：

- `TwoFactorAuth.vue`、`EmailVerification.vue`、`GoogleVerification.vue` 等安全组件不得为了 UI 简化删除流程。
- 修改 2FA 相关组件时必须同时理解请求拦截、410 重放、modal 生命周期和错误处理。
- 开放平台组件不得在页面、toast、console 或错误信息中泄露完整密钥、公钥、回调配置。
- 登录记录、设备、安全设置等组件要保证状态真实来自服务端。
- 业务组件应优先留在业务目录中，只有多页面复用明确时再抽到 `src/components`。

### 8.1 页面内弹窗与抽屉

页面内弹窗和抽屉的组件组织与调用方式参考 `src/views/ucenter/security/components/EmailBindingModal.vue`：

- 弹窗或抽屉作为独立业务组件放在当前页面的 `components/` 目录，文件名使用业务名称加 `Modal` 或 `Drawer`，例如 `EmailBindingModal.vue`。
- 父页面只负责引入组件、声明组件 `ref`、调用 `open(payload)`，并监听 `success` 等业务事件；不得直接修改子组件内部表单和显示状态。
- 子组件内部管理显示状态、表单配置、提交 loading 和关闭逻辑，并通过 `defineExpose` 至少暴露 `open`、`close` 方法。
- `open(payload)` 负责写入本次业务参数并初始化临时状态；`close()` 负责关闭组件。再次打开前必须清理上一次的表单值、校验结果、错误信息和 loading，不能依赖组件重新挂载。
- 提交成功后按顺序执行成功提示、关闭组件和 `emit('success')`；父页面在 `success` 事件中刷新页面数据。提交失败时保留当前输入，展示可理解且不泄露内部信息的错误提示。
- 提交操作必须防止重复触发，并在请求结束时恢复 loading；关闭、接口失败和组件卸载不得留下未恢复的提交状态。
- 弹窗优先使用项目 `FormPupBox` 等现有封装；抽屉优先使用项目已有抽屉容器。容器不同不改变 `open`、`close`、业务事件和状态重置的组件契约。
- 密码、OTP、密钥、证件信息等敏感数据不得写入路由、持久化 Store、日志或错误提示；安全类弹窗和抽屉不得绕过服务端权限、2FA、风控或统一请求处理。

父页面调用保持以下模式：

```vue
<BusinessModal ref="businessModalRef" @success="getInfo" />

<script setup>
import { ref } from 'vue'
import BusinessModal from './components/BusinessModal.vue'

const businessModalRef = ref(null)

const openBusinessModal = (payload) => {
  businessModalRef.value?.open(payload)
}
</script>
```

## 9. View UI Plus 使用规范

可以直接使用 View UI Plus 组件，但必须和项目封装兼容。

要求：

- 表单、表格和弹窗优先使用项目 wrapper；wrapper 不满足时再用 View UI Plus 原生组件。
- 按钮存在适用的项目组件时优先复用；没有覆盖当前按钮语义和交互的项目组件时，可以直接使用 View UI Plus `Button`，不得只为转发原生属性创建无业务价值的包装层。
- 使用 `Modal` 做危险操作确认时，文案必须说明后果，不用模糊的“是否确认操作”。
- 使用 `Message`、toast 时，不输出完整敏感字段或服务端内部规则。
- 原生组件样式覆盖必须 scoped 或限定页面类名，避免全局污染。
- 不直接改 View UI Plus 全局样式，除非是项目主题级需求。

## 10. 组件命名规范

要求：

- 组件文件名使用现有项目风格，保持 PascalCase 或目录 `index.vue`。
- `src/components/form` 中每个共享组件统一使用 `组件名/index.vue` 结构，例如 `src/components/form/FormInput/index.vue`；不得在 `src/components/form` 根目录新增 `.vue` 文件。
- 组件目录使用 PascalCase，并与组件导出名一致；组件专属子组件、资源或配置继续放在该组件目录内，不散落到 `src/components/form` 根目录。
- 全局注册和业务直接导入使用完整的 `@/components/form/<组件名>/index.vue` 路径，避免同一组件同时存在多个导入入口。
- 全局组件名应清晰表达用途，如 `FormDateBox`、`UiTableWap`。
- 业务专用组件不要使用过泛名称，如 `InfoBox`、`NewTable`。
- 新增组件 props、events 命名应贴近现有组件，不创造另一套 API 风格。
- 组件目录命名应与业务或 UI 层级一致，避免散落在无关目录。

## 11. Props、事件与 v-model 规范

要求：

- 不改变已有 props、events、slot 的语义，除非同步迁移所有调用方。
- 新增 props 必须有默认值，避免旧页面运行时报错。
- `v-model` 兼容性优先，不能随意改变值类型。
- 复杂对象 props 不在子组件内直接破坏性修改，除非该组件现有模式就是配置驱动。
- 事件名保持现有风格，如 `on-change`、`search`、`update:modelValue`。
- 共享组件新增能力应保持向后兼容。

## 12. 插槽规范

要求：

- 表格列、操作区、头部按钮等可变内容优先使用 slot。
- slot 名称应与字段名或区域名对应，避免难以理解的临时名称。
- 新增 slot 不应破坏默认渲染。
- 字段级 slot 修改敏感数据时必须继续遵守脱敏规则。
- 不为了一个页面的特殊布局改坏通用 slot 行为。

## 13. 样式规范

组件样式必须遵守 `docs/设计规范.md` 的 Design Token、排版、间距、圆角、状态和可访问性规则。颜色、字号、圆角和断点以当前主题入口及设计规范为唯一详细来源，本文件不重复维护固定值。

要求：

- 页面级样式使用 scoped Less。
- 共享组件样式要避免过深选择器和不必要的 `!important`。
- 状态色、背景、描边、阴影、间距和动效优先使用对应语义 Token。
- 不使用低对比灰字、过度透明、过度阴影和装饰性大渐变。
- 不使用 emoji 作为按钮、菜单、状态的结构性图标。
- 移动端文字、按钮、表单项不能溢出或互相遮挡。

## 14. 响应式规范

断点范围、基准验证宽度、触控区域和 `title` / Tooltip 的详细标准统一遵守 `docs/设计规范.md` 第 3、13、14 节。本节只规定组件在响应式变化时必须保持的兼容边界：

要求：

- 表格、tabs、筛选栏在移动端要可滚动、折叠或卡片化。
- 固定操作栏不得遮挡表单底部按钮或列表内容。
- 不使用固定宽度导致横向溢出。
- 弹窗在移动端应考虑高度、滚动和键盘遮挡。
- 标题与右侧操作使用 Flex 布局时，主要内容容器必须具备正确的收缩能力，按需设置 `min-width: 0`、`flex-shrink` 或换行规则，不能让标题、按钮和状态相互挤压。
- 响应式变化不得改变 props、events、slots、`v-model`、业务顺序、权限判断或敏感信息边界。

## 15. 组件新增或修改影响清单

新增组件前必须确认实际接入页面；修改以下共享组件前必须全局搜索调用方：

```text
UiPage
UiTabs
UiTable
UiTableWap
CardBox
FormTable
FormItemBox
FormInput
FormSelectBox
FormDateBox
FormUpload
FormUploadInput
FormPupBox
FormImg
FormDot
TwoFactorAuth
cardholder/*
```

检查内容：

- 是否影响 KYC/KYB、提现、Recharge、卡片、Express、开放平台、安全设置。
- 该组件当前被哪些页面或业务组件使用。
- 每个受影响页面的影响类型：样式、交互、数据格式、校验、权限、安全、移动端。
- 是否改变 `v-model` 值类型。
- 是否改变默认 loading、empty、pagination、search 行为。
- 是否改变错误提示、确认弹窗、禁用态或防重复提交。
- 是否影响移动端布局。
- 标题、长文案和左右布局是否在最短、最长、多语言和多按钮场景下出现挤压、裁切、跳位或缺少安全的 `title`。
- 是否影响敏感信息脱敏。

新增或修改组件后必须给出影响说明，方便负责人按页面验证。页面局部组件至少列出所属页面；共享或全局组件列出全部直接、间接调用页面；新组件尚未接入页面时明确写“暂无受影响页面”，不得省略本段：

```text
Component Change:
- 新增 / 修改组件：
- 修改内容或新增用途：
- 兼容性：

Affected Pages:
- 页面名称 / 路由：
- 页面文件：
- 影响来源：直接引用 / 全局组件 / 间接依赖 / 动态渲染
- 影响类型：
- 建议验证重点：
- 实际验证结果：已验证 / 未验证及原因
```

影响类型至少从样式、交互、数据格式、校验、props、events、slots、`v-model`、权限、安全、响应式中选择实际命中项，不写笼统的“可能有影响”。

如果调用方很多，可以按业务域归类，例如“财务列表页、卡片详情页、认证动态表单、Express 收付款人列表”，但仍需列出需要优先验证的具体页面名称或路由，不能只给组件文件名。未执行浏览器验证时，影响清单仍需提供建议验证重点，并如实标记未验证。

## 16. 删除或合并组件规范

删除或合并前必须：

- 搜索直接 import。
- 搜索模板标签，包括 PascalCase 和 kebab-case。
- 排除 `src/utils/components.js` 的全局注册噪音后再判断真实使用。
- 检查动态渲染组件、配置驱动组件和业务表单链路。
- 检查 `src/utils/plugin.js`、`src/main.js`、全局注册和导出。
- 给出删除影响说明。

禁止：

- 只看 grep 结果就删除 KYC、cardholder、upload、date、select 类组件。
- 因为只在一个地方使用就一定内联，除非该组件确实没有业务复用价值。
- 删除兼容字段、兼容值类型或旧调用路径。

## 17. 交付要求

组件相关任务使用项目 `AGENTS.md` 的统一交付格式，并额外说明：

- 修改或新增了哪些组件，以及具体改变了哪些行为、样式、props、events、slots 或 `v-model`。
- 按第 15 节格式列出受影响页面名称、路由、页面文件、影响来源、影响类型和建议验证重点；暂无页面使用时也必须明确说明。
- 是否改变调用方兼容性或移动端布局。
- 已检查或验证哪些主要调用场景和边界场景；未验证的页面及原因必须如实列出。
