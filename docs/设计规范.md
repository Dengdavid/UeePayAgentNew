# 设计规范

本文档用于约束 UeePayFrontend 用户端项目的界面设计与前端落地。项目属于金融行业用户端，界面设计必须优先保证可信、清晰、合规、可读、可操作，不以视觉表现牺牲资金展示准确性、认证流程完整性和敏感信息安全。

## 1. 设计定位

UeePayFrontend 同时包含官网展示和登录后用户中心。

设计目标：

- 可信：金融业务界面要稳重、明确、低噪音。
- 高效：用户中心、财务、卡片、Recharge、提现等页面优先信息密度和操作效率。
- 合规：认证、风控、地区限制、协议和资金相关文案必须正式准确。
- 一致：优先复用项目已有组件和主题变量，View UI Plus 原生组件仅作为项目组件无法满足需求时的基础能力补充。
- 响应式：桌面端和移动端都必须可完整操作。

不同场景的设计侧重：

- 官网 / 营销页：可以更有表现力，但不得夸大金融能力。
- 用户中心 / 控制台：安静、清晰、高密度，避免营销化大卡片堆叠。
- 资金 / 卡片 / 认证：优先准确、可审计、可恢复。
- 开放平台：优先配置清晰、密钥安全、错误提示明确。

## 2. 设计 Token

Design Token 的实时定义以 `src/theme/default.less` 为准；`src/assets/css/ui.css` 和 `src/assets/css/com.less` 是消费 Token 的公共样式入口，不维护第二套变量来源。具体色值、Token 数量和完整名称清单不在本文重复登记，使用前必须读取当前主题文件。

### 2.1 层级与使用边界

- 新增设计值遵循 `Primitive 原始值 -> Semantic 语义值 -> Component 组件值`。业务页面优先使用语义 Token，组件 Token 只服务共享组件或明确的复用范围。
- 新增样式前依次检查现有 Token、公共 class 和共享组件；已有能力不得在页面重新硬编码或复制实现。
- 跨页面、跨组件复用或具有稳定语义的颜色、排版、间距、圆角、描边、阴影、层级和动效必须进入主题体系。
- 内容驱动的宽高、响应式计算值和没有稳定复用语义的一次性布局值可以留在局部，不为形式统一制造全局 Token。
- `auto`、`100%`、`fit-content`、`inherit`、`currentColor`、`transparent`、`none` 和清除默认样式的零值属于结构或继承规则，无需 Token 化。
- 组件 Token 必须引用语义 Token；派生背景、边框、悬停、阴影和渐变优先从现有语义值生成，不新增用途相同的近似值。
- 默认尺寸单位为 `px`，变量名不重复携带 `px`；非默认单位应在名称中明确。
- 存量兼容别名只允许旧调用方继续使用；新增或已迁移代码使用当前 `--ui-*` 语义 Token。

### 2.2 视觉语义

- 成功、警告、错误、拒绝、失败、处理和待审核等状态必须沿用现有业务语义，不以视觉统一改变资金、卡片、认证或反馈状态含义。
- 用户中心不使用大面积高饱和渐变；官网或营销页的局部艺术化效果仍应复用已有品牌和状态色。
- 阴影和描边使用主题中已有的完整组合式 Token，不在调用方重新拼接原始参数；状态变化可以只切换语义明确的颜色 Token。
- 圆形、胶囊、透明度和跨组件层级使用现有对应 Token；组件内部简单覆盖关系及框架管理的浮层层级可以保留局部值。
- 共享动效和 `@keyframes` 集中定义并复用，装饰性动画兼容 `prefers-reduced-motion`，状态反馈不得造成闪烁或干扰阅读。
- 全局 Less 中的透明色使用当前编译链已验证的 `rgba()` 或 `color-mix()` 写法，不使用未经验证的新语法。

### 2.3 新增、迁移与验证

- 现有 Token 无法准确表达语义时，才在 `src/theme/default.less` 新增命名清晰的语义或组件 Token，不在单个页面创建近似的平行变量。
- 存量硬编码按当前任务逐步迁移，不因 Token 整理批量重构无关页面。
- 修改全局 Token 前搜索全部调用方，重点核对资金、卡片、认证及成功、警告、错误、处理等状态。
- 修改后验证直接调用页面、共享组件状态、桌面端和移动端；涉及 View UI Plus 主题变量时同步检查对应原生组件。
- 交付说明列出 Token 名称、用途、调用范围、受影响页面或组件及实际验证结果。

## 3. 字体与排版

当前基础：

```less
@font-family: PingFang SC, Microsoft YaHei, Arial, sans-serif !important;
@font-size-base: 13px;
@font-size-large: 14px;
```

字号建议：

| 场景 | 字号 |
| --- | --- |
| 表格 / 表单正文 | 13px |
| 普通说明 / 次级信息 | 12px |
| 卡片标题 / 区块标题 | 14px - 16px |
| 页面标题 | 18px - 22px |
| 官网大标题 | 32px - 48px |

要求：

- 控制台页面不要使用 hero 级大字。
- 正文长文案允许自然换行，但不能挤压按钮、表格、金额或其他关键操作。
- 页面标题、模块标题、卡片标题和表格标题原则上保持单行展示。空间不足时优先为标题保留宽度，仍无法完整展示时使用单行省略，不得通过过度缩小字号强行容纳。
- 横向布局明确不换行时，必须为文字区和相邻板块设置正确的收缩边界，例如 `min-width: 0`、`flex-shrink` 或等效 Grid 约束；任何内容都不得溢出自身区域并被其他板块覆盖。空间不足的文字必须显示省略号，并按本节规则提供绑定同一完整文案的原生 `title`。
- 用户可见文案的内容长度或展示宽度不可控时，必须添加原生 `title`；使用 `text-overflow: ellipsis`、`line-clamp`、固定宽度裁切或其他省略方式时同样必须提供 `title`。
- `title` 必须使用当前语言下允许展示的完整原始文案；动态文案和多语言文案必须与可见文本绑定同一数据源，不得硬编码另一份标题。卡号、证件号、密钥等敏感信息的 `title` 仍只能使用已脱敏内容，不得通过悬停泄露完整值。
- 移动端不能把原生 `title` 作为查看关键信息的唯一方式；关键内容还应支持自然换行、展开、详情页、弹层或其他可触达方式。
- 金额、订单号、卡号尾号等关键数据应使用清晰字重，不要过度装饰。
- 不使用负字距。
- 不用 viewport width 动态缩放字体。

### 3.1 `title` 使用判定

| 场景 | 要求 |
| --- | --- |
| 使用单行省略、多行省略、`line-clamp` 或固定宽度裁切 | 必须添加原生 `title` |
| 标题、表格单元格、文件名、账户名等内容或宽度不可控 | 必须添加原生 `title` |
| 文案允许自然换行且始终完整显示 | 可以不添加 `title` |
| 图标按钮或无可见文字的操作控件 | 不能只依赖 `title`，必须同时提供可访问名称或明确上下文 |
| 移动端关键内容 | 除 `title` 外，还必须提供展开、详情或其他触控可达方式 |
| 桌面端需要完整查看的关键截断内容 | 除 `title` 外，还应提供支持鼠标与键盘触发的 Tooltip、Popover 或详情入口 |
| 卡号、证件号、密钥等敏感信息 | 可见文本和 `title` 均只能使用已脱敏内容 |

## 4. 间距与圆角

基础间距建议：

| Token | 值 | 用途 |
| --- | --- | --- |
| xs | 4px | 图标与文字间距 |
| sm | 8px | 表单内元素、紧凑按钮 |
| md | 12px | 列表项间距 |
| lg | 16px | 卡片内边距、模块间距 |
| xl | 24px | 页面区块间距 |
| xxl | 32px | 官网大区块间距 |

当前组件常用：

- `CardBox` 内边距：16px。
- `UiPage` 默认 padding：16px。
- `UiTabs` gap：12px。

圆角要求：

- 控制台卡片和表单控件以 4px - 8px 为主。
- 不使用大圆角胶囊卡片做信息密集页面容器。
- 胶囊样式只用于状态筛选、标签、轻量 tab。

## 5. 页面布局

登录后页面优先使用：

```text
src/components/uiForm/UiPage
src/components/layout/CardBox.vue
src/components/uiForm/UiTabs
src/components/uiForm/UiTable
src/components/uiForm/UiTableWap
```

布局要求：

- 项目已有组件能够满足需求时必须优先使用，原生 View UI Plus 仅作为项目组件缺少能力时的补充；完整选择顺序、组件清单、封装和调用方检查统一以 `docs/组件使用规范.md` 为详细权威来源。
- 使用原生 View UI Plus 组件时，应保持项目主题、交互、响应式和状态处理一致，并在交付说明中记录现有项目组件无法满足的原因；不得为了减少原生组件而创建无业务价值的空包装层。
- 列表页优先使用 `UiPage` 承接标题、筛选、状态、表格、分页和移动端搜索。
- 独立信息区块使用 `CardBox`。
- Tab 页面使用 `UiTabs`，不要重复造 tab 样式。
- 模板中的 `div` 等容器优先复用项目已有原子化布局 class，并优先使用 Flex / Grid 等结构化布局完成排列、对齐和间距，避免为常见布局重复新增页面级选择器。
- 只有现有组件、公共 class 和结构化布局无法满足需求时才新增样式；Vue 单文件组件统一使用 `<style lang="less" scoped>`，独立样式文件使用 `.less`，不得新增普通 CSS 写法。存量 CSS 不在无关任务中批量迁移。
- 页面主内容应左对齐，除官网标题、空状态和认证引导外，不默认居中。
- 不要把大区块做成卡片套卡片。
- 详情页优先保持字段分组清晰，不做复杂装饰。
- 使用左右分布时，必须先明确两侧内容的主次关系、最小宽度和允许收缩范围，并使用最短、最长、多语言和动态内容验证挤压情况。
- 核心内容优先保留空间；次要信息和操作区不得无限挤压标题、金额、状态或主要内容。Flex 子项需要收缩时应正确设置 `min-width: 0`、`flex-shrink` 或 `flex-wrap`，避免内容溢出或异常撑宽。
- 标题受挤压时按第 3 节执行单行省略和 `title` 规则；操作按钮不得被压缩到文字重叠、按钮变形或触控区域过小。
- 同一行无法合理容纳左右内容时，应在合适断点切换为上下布局、换行布局或将低优先级操作收纳到“更多操作”，不得通过过度缩小字号或间距强行维持左右结构。
- 左右布局切换后必须保持信息顺序、按钮业务顺序和视觉层级一致，不得因响应式变化改变操作语义。

用户中心推荐结构：

```text
页面标题
关键提示 / 合规提示
统计概览
筛选条件 / 操作按钮
表格 / 列表
分页 / 加载更多
弹窗 / 抽屉
```

## 6. 表格与列表

表格适用于：

- 财务流水。
- Recharge / Withdrawal 记录。
- 卡片 / 持卡人 / 交易列表。
- 登录记录、消息、开放平台配置记录。

要求：

- 表头清晰短句，不用长段描述。
- 金额列右对齐或保持统一视觉对齐。
- 状态列使用统一状态色和文案。
- 操作列只放当前行动作，批量动作放在表格上方。
- 敏感字段必须脱敏，如卡号、邮箱、手机号、证件号。
- 长订单号、交易号、Webhook URL 应支持复制，但默认不打断布局。
- 空状态必须说明当前无数据，不要显示接口字段或调试文本。

移动端：

- 使用 `UiTableWap` 或卡片式列表。
- 搜索入口可使用 `UiPage` 的移动端浮动搜索。
- 行动按钮固定到底部时必须避免遮挡内容。

## 7. 表单设计

表单优先使用：

```text
src/components/form
src/components/uiForm
```

要求：

- 项目已有表单组件能够满足需求时必须优先使用，不得直接使用原生组件重复实现已有能力。
- 现有项目组件确实无法满足业务或交互要求时，才允许直接使用 View UI Plus 原生组件；使用前必须说明缺失能力和选择原生组件的原因，不得为了方便绕过项目组件。
- 具体表单组件映射、兼容范围和调用方检查统一遵守 `docs/组件使用规范.md`，本规范不重复维护容易漂移的完整组件清单。
- label 使用清晰业务名。
- 必填项使用组件能力，不手写散落星号。
- placeholder 只提示输入方式，不替代 label。
- 说明文案放 `desc` 或提示区域，不塞进 placeholder。
- 校验文案使用多语言 key。
- 复杂表单按业务分组，避免长表单无结构。
- 危险操作使用二次确认。

认证 / KYB 动态表单：

- 服务端字段配置为准。
- 不通过前端隐藏必填字段绕过认证。
- 父子联动字段变更时保留用户可理解的确认流程。
- 文件上传要说明格式、大小、用途和隐私保护。

## 8. 按钮与操作

按钮优先复用适用的项目组件。当前没有适用的项目封装时，可以使用 View UI Plus `Button` 作为通用按钮基础；不得只为转发原生属性创建无业务价值的按钮包装层。

优先级：

- 主按钮：页面主动作，如提交、确认、发起申请。
- 默认按钮：次要动作，如取消、返回、刷新。
- 文本按钮：低风险辅助动作，如查看详情、复制。
- 危险按钮：删除、注销、冻结、重置密钥等高风险动作。

要求：

- 一个操作区最多一个主按钮。
- 资金、卡状态、密钥、认证提交必须有明确确认。
- 不使用颜色相近的多个主按钮并排。
- loading 状态必须防止重复提交。
- 按钮文案使用动词，如“提交申请”“确认提现”“复制密钥”。
- 同一页面中相同层级和相同业务作用的按钮，位置、顺序、尺寸和对齐方式应保持一致；不一致时必须有明确业务原因。
- 页面级操作优先使用共享页面容器提供的标准操作区：无筛选栏时放在标题区域，有筛选栏时与筛选操作统一排列，移动端使用底部安全操作区。模块级操作放在模块标题右侧，表格行操作放在操作列，弹窗和表单操作放在底部操作区。
- 取消、确认和危险操作的排列顺序必须在同类场景中保持一致；权限或状态变化导致按钮不可用时，优先使用禁用、占位或统一收纳策略，避免同级按钮频繁跳位。
- 移动端可以将页面级操作调整到标题下方或底部安全操作区，也可以改变排列方向，但必须保持按钮业务顺序、主次层级和可达性一致。

修改本节公共视觉样式前，必须实时搜索全部调用方，并验证代表性页面的桌面端、移动端及该样式适用的交互和可访问性状态；CTA 至少覆盖 disabled、loading 和 `prefers-reduced-motion`。调用关系以实时搜索结果为准，不在本文档维护容易过期的页面清单。

### 8.1 公共强调型 CTA 按钮

官网、公开营销页或业务引导页的唯一主行动按钮，优先使用全局公共样式 `ui-cta-button`。样式定义位于：

```text
src/assets/css/com.less
```

基础用法：

```vue
<Button type="primary" class="ui-cta-button">
  立即申请
  <Icon type="ios-arrow-round-forward" />
</Button>
```

该样式统一提供：

- 基于 `var(--ui-color-primary)` 派生的主色渐变。
- `8px` 圆角、轻量投影，以及悬停上浮和按下反馈。
- 每 `3.6s` 触发一次的低强度扫描光。
- disabled 状态停止扫描光。
- 系统开启 `prefers-reduced-motion: reduce` 时自动关闭动画。

使用要求：

- 仅用于页面或操作区唯一的主行动按钮，例如“立即汇款”“立即联系客服申请”。
- 普通提交、取消、返回、表格操作、危险操作和用户中心高频按钮继续使用 View UI Plus 原有按钮类型，不添加扫描光。
- 页面可以通过自身 class 调整高度、宽度和内边距，但不得复制渐变、投影、扫描光 keyframes 或重新实现同类动画。
- 新页面需要相同 CTA 效果时，直接为 View UI Plus `Button` 添加 `ui-cta-button`，避免新增页面级重复样式。
- 仅需在原按钮视觉基础上增加扫描光时，使用 `ui-button-shine`，该类不会修改按钮的圆角、背景、字重、投影或悬停反馈。

### 8.2 公共功能图标容器

官网首屏、公开营销页和业务说明卡片中的功能图标，统一使用全局公共样式 `ui-feature-icon`。样式定义位于：

```text
src/assets/css/com.less
```

基础用法：

```vue
<span class="ui-feature-icon">
  <Icon type="md-flash" aria-hidden="true" />
</span>
```

成功或完成语义使用公共变体：

```vue
<span class="ui-feature-icon ui-feature-icon--success">
  <Icon type="md-checkmark" aria-hidden="true" />
</span>
```

该样式统一提供：

- `50px` 图标容器、`16px` 圆角及 `28px` 图标字号。
- 基于 `var(--ui-color-primary)` 派生的浅色层次与内高光，不添加容器或图标投影。
- 同时兼容 View UI Plus `.ivu-icon` 与项目 `.iconfont`。
- `ui-feature-icon--success` 用于成功、完成或接收端语义，不能单独替代文字状态。

使用要求：

- 新页面直接调用公共 class，不复制背景、圆角、投影或伪元素样式。
- 图标名称、语义、可访问性及敏感场景要求继续遵守 `docs/图标使用规范.md`。
- 页面可以在响应式场景通过 CSS 变量或自身 class 调整容器尺寸，但不得改变同一信息层级中的图标一致性。

## 9. 状态与反馈

状态必须和业务语义一致。

推荐状态色：

| 状态 | 颜色 |
| --- | --- |
| 成功 / 已通过 / 正常 | `@success-color` |
| 审核中 / 处理中 / 待确认 | `@primary-color` 或中性蓝 |
| 警告 / 待补充 / 待操作 | `@warning-color` |
| 失败 / 拒绝 / 已关闭 | `@error-color` |
| 禁用 / 未开始 | `@subsidiary-color` |

反馈要求：

- 成功提示说明操作结果。
- 失败提示说明可行动原因，不暴露后端堆栈。
- 网络错误、限流、地区限制、2FA 必须保持项目现有处理。
- 财务操作不要在“提交成功”时表达为“到账成功”。

## 10. 金额、卡片与敏感信息

金额展示：

- 使用项目金额工具或 `decimal.js` 处理计算。
- 金额小数位、币种、正负号保持一致。
- 手续费、总额、余额要明确区分。
- 不用红绿表达金额涨跌以外的含义，避免误读。

卡片信息：

- 默认展示脱敏卡号。
- CVV、完整 PAN、OTP 不得直接常驻展示。
- 私密信息查看必须受服务端权限、2FA 和风控结果控制。
- 冻结、解冻、注销、转入、转出必须有明确确认。

开放平台：

- 密钥、公钥、Webhook、IP 白名单页面要突出安全风险。
- 密钥类信息默认隐藏或最小展示。
- 复制成功提示不包含密钥原文。

## 11. 图标与视觉资产

图标来源、实现、命名、语义和可访问性统一遵守 `docs/图标使用规范.md`。设计评审只额外确认同类操作的图标一致、图标没有替代关键文字说明，且图标风格与当前信息层级匹配。

官网和营销页可使用视觉资产，但必须服务于真实业务说明，不使用与金融能力无关的纯装饰背景。

## 12. 多语言与文案

用户可见文案的 i18n、Locale 同步、fallback、格式化、RTL 和翻译质量统一遵守 `docs/多语言规范.md`。设计评审只额外确认长文本和 RTL 不破坏布局，金融、认证、风控与协议文案没有使用“秒到”“保证通过”“无限制”“免审核”等承诺。

## 13. 响应式与移动端

实现断点以当前项目习惯为基础：

```css
@media screen and (max-width: 768px) {}
```

设计评审至少覆盖以下宽度范围：

- 移动端：`<= 768px`。
- 平板端：`769px - 1199px`。
- 桌面端：`>= 1200px`。
- 基准验证宽度至少包含 `375px`、`768px`、`1024px` 和 `1440px`，并与 `docs/组件使用规范.md` 保持一致。
- 关键页面还需检查项目支持范围内的最小屏幕、超宽屏幕和浏览器缩放场景。

响应式要求：

- 移动端不能只是桌面端等比例缩小，必须根据任务优先级重新排列内容、导航和操作。
- 桌面端多列布局在平板或移动端空间不足时，应切换为少列、单列、上下排列、可控横向滚动或分步展示。
- 桌面端采用不换行加省略的横向内容，在移动端默认改为自然换行并完整展示；如果响应式设计已经把相关区域切换为上下堆叠，且各层内容完整可达，则不要求在每个堆叠层内部额外换行。
- 表格在小屏幕下优先使用 `UiTableWap`、卡片列表、字段折叠或可控横向滚动，并保留关键数据与核心操作。
- 图表必须随容器宽度变化，并保证坐标轴、图例、标签、Tooltip、单位和异常值可读；不得裁掉关键数据。
- 复杂弹窗在移动端应根据内容量评估使用全屏页面、抽屉或底部面板；表单由多列切换为单列时必须保持字段业务顺序。
- 标题、左右分布和同级按钮在断点变化时，分别遵守第 3、5、8 节的单行、挤压和位置一致性要求。

移动端要求：

- 核心流程完整可操作。
- 表格转为卡片或 `UiTableWap`。
- 搜索、刷新、返回、加载更多必须可达。
- 固定底部按钮不能遮挡内容。
- 抽屉高度不超过视口安全范围。
- 高频点击和关键操作的触控区域建议不小于 `44px × 44px`，并与 `docs/组件使用规范.md` 保持一致。

桌面端要求：

- 信息密度高但不拥挤。
- 筛选项和操作按钮在首屏可见。
- 表格列宽和操作列稳定。
- 列表、详情、弹窗之间路径清楚。

### 13.1 边界场景

设计和前端落地不能只验证理想数据，关键页面和组件至少检查：

- `0`、空值、缺失值、未知值、负数、极小值、极大值和超出预期范围的数值。
- 不同币种、小数位、高精度金额、百分比超出常规区间，以及金额正负号、币种和单位组合。
- 最短文案、最长文案、多语言扩展、特殊字符、连续数字、超长文件名、账户名、订单号和 URL。
- 空列表、单条数据、大数据量、全部相同的图表数据、差异悬殊的数据和异常峰值。
- 慢请求、失败、重复提交、部分加载失败、权限不足、账户受限、操作过期和并发状态变化。
- 最小屏幕、平板、桌面、超宽屏幕、浏览器缩放及横竖屏变化。

边界场景必须明确采用完整展示、省略、换行、滚动、折叠、校验、禁用或异常反馈中的哪种处理方式；出现重叠、遮挡、异常换行、按钮跳位、横向溢出或关键数据不可达，均视为未通过设计验收。

### 13.2 UI 归一化

- 优先使用项目现有 Design Token 和共享组件统一响应式断点、内容宽度、栅格、间距、字号、行高、圆角、控件高度、状态颜色和反馈状态，不为单个页面散落无规律的特殊值。
- 金额、数字、百分比、日期、时间、表格列宽和文本溢出规则必须在同类场景保持一致；金额计算继续遵守第 10 节的高精度要求。
- 相同信息层级的标题、按钮、状态、表单、卡片和反馈应使用相同的视觉与交互规则；业务差异不足以改变语义时不得新增页面专属表现。
- 加载、空状态、错误、无权限、网络异常和受限状态应复用统一组件与反馈层级，不为相同语义创建多套表现。

### 13.3 数据归一化

- 不同量纲的数据不得直接进行视觉比较。根据业务语义选择原始值、百分比、同比/环比、单位时间值、指数、`0-1` / `0-100` 标准化或对数刻度，并保留可查看的原始值。
- 数据归一化必须说明计算方式、原始单位、统计周期和异常值处理规则，不得通过裁剪坐标轴、隐藏原始值或省略单位制造误导。
- 未经归一化也能清晰比较的同单位数据应优先展示原始值，不为了视觉整齐进行无业务价值的转换。
- 归一化后的数值不得替代资金、费率、余额、交易数量等用户需要核对的原始业务数据。

### 13.4 图表与数据可视化

- 需要精确查找、排序、筛选或核对单笔数据时优先使用表格；需要观察趋势、分布、构成或异常时才使用图表。
- 趋势优先使用折线图，类别比较优先使用柱状图；占比类别不超过 5 类且确需表达构成时才使用饼图或环图。
- 图表必须明确标题、指标定义、单位、统计周期、数据更新时间和数据来源范围，不使用含义不明的缩写。
- 坐标轴是否从零开始必须由数据含义决定；截断坐标轴、双坐标轴、对数刻度和归一化展示必须明确标识，避免夸大变化。
- Tooltip 必须显示原始值、单位和时间范围；百分比、同比、环比和累计值必须清楚区分。
- 图表需要覆盖无数据、单点数据、全部相同、差异悬殊、异常峰值、部分加载失败和数据延迟状态。
- 无数据时显示明确空状态，不保留没有解释价值的空坐标轴；加载失败时提供错误说明和可用的重试入口。
- 大量数据优先分页、聚合或按需加载，不在页面一次渲染全部明细；金额、日期和数字使用项目统一格式与稳定对齐方式。
- 不只依赖颜色区分系列，应同时使用标签、图例、线型、形状或文字说明；重要结论应提供可读的文字摘要。
- 响应式状态下不得裁掉关键数据。空间不足时优先减少非关键标注、调整图例位置或切换为适合小屏幕的表达，不得单纯缩小到不可读。

## 14. 可访问性

基础要求：

- 普通文本与背景的对比度不低于 `4.5:1`，大号文本及关键非文本界面元素不低于 `3:1`；品牌表达不得覆盖可读性要求。
- 不只依赖颜色表达状态，应配合文字。
- 所有核心流程必须支持键盘完成，交互顺序与视觉顺序一致，焦点样式不得被无替代地移除。
- 表单错误提示靠近字段，并与对应字段建立可识别关系；错误出现后应提供明确的修正方式。
- 图标按钮要有明确语义和可访问名称，不能只依赖图标外观或原生 `title`。
- 弹窗打开后焦点进入合理位置，关闭后返回触发元素；弹窗内部焦点顺序清晰，不能落到被遮挡页面。
- loading、disabled、empty 状态必须可区分。
- 页面在浏览器 `200%` 缩放和项目支持的最小屏幕下仍应保持核心内容与操作可达，不出现必须双向滚动才能完成的关键流程。
- 装饰性动画遵守 `prefers-reduced-motion`；自动播放、闪烁或持续位移动画不得干扰金融数据阅读和操作。

禁用态：

- 禁用原因要可理解。
- 资金、认证、卡片权限不足时应说明下一步动作，如“完成认证”或“联系客服”。

## 15. 官网与营销页

官网页面包括首页、卡片、Express、定价、合作、帮助中心。

要求：

- 第一屏要清楚展示 UeePay / 优易付和核心服务。
- 可以使用更大的标题、图片、品牌色和模块节奏。
- 不使用纯装饰 SVG 或无业务含义的渐变堆叠。
- 不承诺不确定金融结果。
- CTA 文案清晰，如“立即注册”“查看方案”“联系客服”。
- 移动端首屏不能只有装饰图，必须可理解服务内容。

## 16. 控制台与用户中心

用户中心页面包括财务、Recharge、提现、卡片、持卡人、安全、开放平台、消息等。

要求：

- 不做营销 hero。
- 不使用大面积插画占据高频操作区域。
- 统计数据、筛选、表格和操作优先。
- 危险操作和资金操作流程必须稳定。
- 高频页面要减少无意义过渡动画。
- 详情页字段顺序应符合业务阅读顺序。

## 17. 设计与落地流程

- 修改前查看当前页面、相邻页面、共享组件和 Design Token，确认必须保持的数据、接口、权限、流程与移动端行为。
- 业务流程、金额、权限、认证、风控、敏感信息或合规表达存在关键歧义时停止确认；非关键假设可以说明后继续。
- 只有新页面、整体重设计、信息架构调整或确有多个重要方向时，才提供 2～3 个精简方案、差异和推荐理由，并在实施前取得确认。
- 用户已指定方向，或任务只是文案、间距、颜色、图标、错位、响应式、可访问性和兼容性修复时，可以直接设计或实施。
- 落地时复用现有组件和样式体系，同步考虑多语言、移动端、安全边界，并说明共享组件的受影响页面和验证范围。

### 17.1 设计交付验收清单

设计交付前至少确认：

- 信息层级、页面主任务和主要操作是否清晰。
- 页面、模块、卡片和表格标题是否避免非必要换行；被省略或宽度不可控的文案是否按第 3 节提供安全的 `title`。
- 同级按钮的位置、顺序、尺寸、主次和响应式变化是否一致。
- 左右布局是否使用最短、最长、多语言、动态内容和多按钮场景验证，是否存在挤压、遮挡、跳位或横向溢出。
- 桌面端、平板端、移动端、最小屏幕、超宽屏幕和浏览器缩放下，核心内容与操作是否完整可达。
- `0`、空值、缺失值、负值、极值、超长文案、大数据量和异常状态是否具有明确处理。
- 金额、币种、单位、精度、时间和状态语义是否一致，归一化数据是否保留原始值且不会误导。
- loading、empty、error、disabled、无权限、网络异常、操作过期和部分失败状态是否覆盖。
- 卡号、证件号、密钥、OTP 等敏感信息在可见文本、`title`、Tooltip、错误信息和复制结果中是否保持安全边界。
- 键盘、焦点、对比度、触控区域和减少动态效果是否满足第 14 节。
- 是否优先复用项目已有组件和 Design Token；使用原生 View UI Plus 或新增样式时是否有明确理由。

本清单定义设计交付的检查内容，具体测试层级、浏览器验证、构建触发和证据记录统一遵守 `docs/测试规范.md` 与 `docs/构建发布与性能规范.md`，不在本文档重复定义。

## 18. 禁止事项

- 禁止为用户中心页面制作营销式 hero。
- 禁止使用大面积单一渐变背景替代信息结构。
- 禁止把卡片嵌套卡片作为默认布局。
- 禁止用颜色或图标单独表达重要状态。
- 禁止完整展示 PAN、CVV、OTP、密钥、证件号。
- 禁止通过前端视觉隐藏绕过权限、认证、风控或地区限制。
- 禁止新增与现有组件体系冲突的 UI 框架。
- 禁止为了视觉效果降低表格、表单、金额和状态的可读性。
